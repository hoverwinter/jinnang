# 系统精读技能

像学生一样读书——顺序推进、记录疑问、交叉引用、螺旋深化。

## 核心理念

**不要跳读。** 作者会在后续章节螺旋式深化概念。前文看似模糊的内容，读到后面自然清晰。记录疑问，继续往下读，答案往往在后头。

## 工作流程

### 0. 准备阶段

1. **定位图书文件**
   - 检查 `raw/books/` 或其他用户指定路径
   - 确认文件名（含特殊字符的文件名用 `ls -la` 获取全名）
   - 记录总页数或总章节数

2. **创建进度追踪文档**

   在 `wiki/` 下创建 `.<书名>阅读进度.md`：

   ```markdown
   ---
   type: reading-progress
   name: <书名>阅读进度
   created: YYYY-MM-DD
   updated: YYYY-MM-DD
   book: <书名>
   total_pages: N
   source: raw/books/<文件名>
   ---
   
   ## 全书框架
   
   ### 结构概览
   - Part/卷划分
   - 各部分核心主题
   
   ### 核心概念清单
   - 基础概念（反复出现、后续依赖）
   - 衍生概念（基于基础概念）
   
   ### 作者写作逻辑
   - 螺旋式/模块式/递进式
   
   ### 核心章节标记
   - 必读章节（概念核心定义）
   - 可略章节（边缘内容、补充案例）
   
   ## 进度表
   
   | 日期 | 章节 | 状态 |
   |------|------|------|
   | YYYY-MM-DD | Ch 1-3 | 进行中 |
   
   ## 章节摘要
   
   ### Ch 1: 标题
   - 关键点1
   - 关键点2
   
   ## 疑问清单
   
   ### 疑问 #1: 标题
   **章节**: Ch X
   **原文**: "..."
   **疑问**: 
   - 问题点
   **解答**: （待后续章节解答）
   
   ---
   
   *最后更新: YYYY-MM-DD*
   ```

3. **确定阅读节奏**
   - 默认每轮 3-5 章（技术书约 100-150 页）
   - 用户可指定节奏："每天读 2 章"、"一次读完"
   - 若用户说"不需要确认，依次精读"，则全速推进

### 1. 略读建立框架

**先建地图，再走路。** 花 10-15 分钟略读全书，建立"导航图"。

略读目标：

1. **提取目录结构**
   - 读取目录页（PDF 目录或 TOC）
   - 识别 Part/卷划分，每部分主题
   
2. **识别核心概念**
   - 略读每章开头 1-2 页（引言、定义段落）
   - 列出反复出现的概念名
   - 标记层级：基础概念（被反复引用） vs 衍生概念
   
3. **判断作者写作逻辑**
   - **螺旋式**：同一概念多章节反复深化（如 Al Brooks）
   - **模块式**：每章独立主题，弱依赖（如参考手册）
   - **递进式**：线性推进，前章是后章基础（如教材）
   
4. **标记核心章节**
   - 概念首次完整定义的章节 → 必读
   - 补充案例/边缘应用的章节 → 可略读
   - 后续精读时可据此调整节奏
   
5. **更新进度文档**
   - 填写"## 全书框架"部分
   - Git 提交：`git commit -m "框架: <书名> 目录+概念清单"`

**略读不等于跳读。** 略读是建框架，精读是填充细节。略读时只看：
- 章节标题和小标题
- 引言/总结段落
- 关键术语首次出现的定义句

不看：详细论证、案例分析、图表解读。

### 2. 顺序精读

**禁止跳读。禁止回头看。读到不懂的地方——记下来，往下读。**

每轮阅读：

1. **提取章节内容**
   - PDF 用 `pdftotext`（注意 PDF 页码 ≠ 书页码，需核对目录）
   - Markdown/文本直接读取
   
2. **生成章节摘要**
   - 3-5 个关键要点（bullet 格式）
   - 不追求详尽，抓核心概念
   
3. **记录疑问**
   - 遇到不理解的内容，立即记录
   - 格式见上方模板
   - **不要停下来思考太久**——记下来，往下读
   
4. **检查疑问是否可解**
   - 新章节读到某处，突然理解了之前疑问
   - 在疑问条目下添加"解答"部分，标注章节来源
   
5. **更新进度表**
   - 标记章节状态：进行中 → 已完成
   
6. **Git 提交**
   - 每轮完成后提交：`git add wiki/.<书名>阅读进度.md && git commit -m "进度: <书名> Ch X-Y"`

### 3. 疑问交叉引用系统

疑问不是问题——是**锚点**。读到后面，作者会回答。

**记录格式**：
```markdown
### 疑问 #N: 主题
**章节**: Ch X（疑问产生的位置）
**原文**: "原文片段"
**疑问**: 
- 具体不理解什么
**解答**: Ch Y 第 Z 页解释了："..."
```

**解答来源标注**：
- 必须写明"来自 Ch Y"或"第 Z 页"
- 不能写"后续章节"这种模糊来源

**疑问状态**：
- 待解：解答字段留空或写"待后续章节解答"
- 已解：填写解答和来源章节
- 全书读完仍有疑问：标注"未解决"，建议用户单独讨论

### 4. 螺旋深化理解

作者写作规律：
- **首次引入**：概念定义，基本示例
- **二次出现**：变体、边界情况
- **三次深化**：与其他概念联系、实战应用

因此：
- 前几章的疑惑是**故意留白**
- 不要在第一章纠结"为什么这样"
- 记下来，继续读，答案在后面

### 5. 完成阶段

1. **整理疑问清单**
   - 检查所有疑问是否已解答
   - 未解答的标记并汇总
   
2. **全书总结**
   - 在进度文档末尾添加"## 全书总结"部分
   - 核心方法论/框架提炼（5-10 条）
   - 可建立 `wiki/concepts/` 概念页面
   
3. **最终 Git 提交**
   ```bash
   git add wiki/.<书名>阅读进度.md
   git commit -m "完成: <书名> 系统精读"
   ```

4. **可选：创建概念页面**
   - 重要的概念可提炼到 `wiki/concepts/<概念名>.md`
   - 添加 frontmatter 和来源引用

## 常见问题

### Q: PDF 页码和书页码不一致怎么办？

用 `pdftotext` 前，先检查目录（TOC）：
- 书目录显示"第13章 第145页"
- 实际 PDF 可能第 227 页才是第13章开始
- 需要手动核对，或让用户提供目录页码对应关系

### Q: 用户中途打断怎么办？

当前进度已 Git 提交，下次可以：
1. 读取进度文档看已完成章节
2. 从上次停止处继续

### Q: 需要用户确认吗？

默认每个阶段确认。若用户明确说"不需要确认，依次精读"，则全速推进直到读完。

### Q: 疑问太多怎么办？

正常现象。Al Brooks 四卷读完记录了 15 个疑问，全部在后续章节解答。
- 疑问数量 ≠ 理解质量
- 疑问是阅读过程的自然产物
- 答案在后面，这是作者的设计

## 示例

用户说："帮我精读 Al Brooks 的价格行为四卷"

执行：
1. 检查 `raw/books/` 定位 PDF 文件
2. 创建 `wiki/.Al Brooks阅读进度.md`
3. **略读建立框架**：
   - 提取目录：4 卷（趋势、反转、区间、实战）
   - 识别核心概念：信号柱、趋势线、通道、支撑阻力、突破、反转形态
   - 判断写作逻辑：螺旋式（同一概念多卷反复深化）
   - 标记核心章节：每卷前 3 章是概念定义核心
4. 确认节奏："四卷共2632页，建议每轮约150页（3-5章），是否需要我每次确认再继续？"
5. 用户说"不需要确认，依次精读" → 全速推进
6. 每轮：提取章节 → 记摘要 → 记疑问 → 检查解答 → Git 提交
7. 完成后整理疑问清单，全书总结，Git 提交

---

**记住**：先建框架，再精读。略读是建地图，精读是走路。有了导航图，疑问就知道"大概会在哪里解答"。
